EIP-7702 and the Binance incident: delegated execution explained

Research published 1 November 2026 · am3rix · Read-only public evidence

The October 2026 incident has been linked to an Ethereum type-4 authorization and subsequent asset movement. This guide explains what the mechanism does, how a reader can inspect it, and which claims remain outside the public evidence.

What is EIP-7702?

EIP-7702 allows a transaction to carry one or more signed authorizations that designate code for an externally owned account. Each authorization contains a chain identifier, delegate address, nonce and signature components. Protocol validation determines whether an authorization may update account state. Merely seeing signatures in the transaction does not mean every authorization took effect.

What does a delegation designator do?

An effective authorization can set account code to a special prefix, 0xef0100, followed by a 20-byte delegate address. When that account is subsequently called, delegated code can execute in the account's context. Crucially, this changes execution semantics; it does not establish that the protocol's signature checks were broken.

What was unusual in the cited transaction?

The incident analysis associates transaction 0xad9926…298b with an authorization list containing 50 tuples. The fact that many tuples appear is distinct from the number that the Ethereum state machine accepted. Investigation requires examining effective nonce matches and any resulting code changes.

What follows from the transaction order?

The subsequent sweep transaction is recorded in a later block. A public node can return each transaction's envelope and receipt. Event logs show resulting token transfer events, but logs should not be assumed to prove beneficial ownership or the attacker's identity.

Where can the signature have come from?

The chain can prove cryptographic validity within protocol rules. It cannot distinguish coerced approval, compromised signing infrastructure, stolen key material or a compromised operator workflow. Public reporting describes possible internal compromise, but the code path that produced the signatures is not recoverable from block data alone.

Defensive lessons

Controls worth evaluating include independent signing-intent verification, delegation-change alerts, policy-enforced recipient and method restrictions, withdrawal exposure limits, and documented emergency revocation. These are general controls; they should not be read as a verified description of Binance's actual systems.
